# tradingAI — Binance 선물 자동매매 봇 & 실시간 대시보드

Freqtrade 기반 바이낸스 선물 자동매매 시스템입니다. AWS EC2에 24/7 배포되어
Telegram 실시간 알림 + 자체 제작 웹 대시보드로 모니터링합니다.

**현재 운용 중인 전략은 `BoxBreakoutV2Strategy`(박스권 돌파) 하나이며, 레버리지 3배,
동시 포지션 3개로 소액 실계좌에서 돌고 있습니다.** 원래 운용하던 두 전략(추세추종 /
평균회귀)은 2026-08-27 진입 신호 검증에서 **통계적 엣지가 없음이 확인되어 중단**했습니다
(Phase 8 참고). 이 저장소에 그 두 전략 코드가 남아 있는 것은 검증 과정의 기록이며,
현재 가동되는 봇이 아닙니다.

> ⚠️ 이 저장소는 포트폴리오/학습 목적입니다. 실제 API 키, 서버 접속 정보,
> 거래 DB 등 민감 정보는 전부 제외했습니다 (`.gitignore`, `.env.example` 참고).
> 코드를 그대로 실행한다고 해서 수익이 보장되지 않으며, 실전 투입 전 반드시
> 본인 책임 하에 충분한 드라이런 검증을 거쳐야 합니다.

## 1. 전체 구조

```
tradingAI/
├── freqtrade/                  # 메인 실전 봇 (Freqtrade)
│   ├── strategies/
│   │   ├── BoxBreakoutV2Strategy.py     # ★ 현재 실전 운용 — 박스권 돌파 (롱/숏)
│   │   ├── BoxBreakoutStrategy.py       # 위 전략의 v1 (격자탐색에서 v2에 밀려 중단)
│   │   ├── MultiConfluenceStrategy.py   # 추세추종 — 엣지 없음 확인 후 중단 (기록용)
│   │   └── MeanReversionStrategy.py     # 평균회귀 — 엣지 없음 확인 후 중단 (기록용)
│   ├── config_boxbreakout_v2_futures.json  # 실전 설정 (3x, 동시 3포지션)
│   ├── walk_forward.py                  # 워크포워드 최적화 자동화 (Docker hyperopt 반복실행)
│   ├── docker-compose.yml               # 봇 + 대시보드 컨테이너 오케스트레이션
│   └── dashboard/                       # 자체 제작 Flask 웹 대시보드
├── tools/                       # 교차검증용 보조 엔진 (VectorBT, Backtrader, CCXT)
│   └── signal_alert.py          # 바이낸스 → 텔레그램 신호 알리미 (로컬 전용, 미배포)
├── experimental/                # 실험 트랙 (FinRL, Hummingbot, NautilusTrader 등)
└── aws/                         # EC2 배포용 cloud-init 스크립트
```

## 2. 개발 과정 (진행 순서)

### Phase 1 — 환경 세팅 & 검증 파이프라인
- Freqtrade를 Docker 기반으로 세팅, `.env`로 API 키/시크릿 분리 (하드코딩 금지)
- VectorBT(대량 파라미터 스캔) → Freqtrade hyperopt(정밀 검증) → Backtrader(교차검증)
  세 엔진으로 결과 방향성을 상호 검증하는 구조로 실험 스크립트 정리

### Phase 2 — 전략 개발 & 워크포워드 최적화
> ⤷ **Phase 8에서 폐기됨** — 여기서 만든 두 전략 모두 진입 신호에 엣지가 없는 것으로
> 확인되어 중단했습니다. 아래는 당시 기록입니다.

- **MultiConfluenceStrategy** (추세추종): MACD + Stochastic + Bollinger Band 컨플루언스
- **MeanReversionStrategy** (평균회귀): RSI + Bollinger + ADX 국면 필터
- 자체 제작 `walk_forward.py`로 90일 학습 / 30일 검증 롤링 윈도우 최적화 자동화
  (Docker로 hyperopt 반복 실행 후 CSV 결과 축적)
- 5x 레버리지 선물 기준 워크포워드 결과 (21개 구간 평균, `freqtrade/walk_forward_results_*_5x.csv`):

  | 전략 | 검증 구간 수 | 구간당 평균 수익률 |
  |---|---|---|
  | MultiConfluenceStrategy (추세추종) | 21 | +3.90% |
  | MeanReversionStrategy (평균회귀) | 21 | +6.48% |

  > 위 수치는 당시 워크포워드 결과의 기록이며 현재 운용 성과가 아닙니다.

### Phase 3 — 고위험/고수익 확장 (선물 롱숏 + 레버리지)
> ⤷ **Phase 8에서 변경됨** — 레버리지는 5배가 아니라 **3배**입니다. 여기서 5배로
> 정한 근거는 이후 손절 버그(Phase 8)가 섞인 백테스트였습니다.
> `can_short`를 `@property`로 두는 부분은 지금도 유효합니다.

- 두 전략 모두 현물 롱 전용 → **선물 롱/숏 양방향 + 설정 가능한 레버리지**로 확장
- `can_short`를 클래스 속성이 아닌 `@property`로 구현
  (`trading_mode == "futures"`일 때만 동적으로 True — freqtrade는 spot 설정에서
  `can_short=True`를 클래스 속성으로 두면 시작 시점에 하드 에러를 냄)
- 리스크 수준(레버리지)을 사용자와 함께 단계적으로 검증 후 5배로 확정

### Phase 4 — 알림 & 대시보드
> ⤷ **Phase 9에서 확장됨** — 아래 내용은 그대로 유효하고, 봇 전원 버튼·진입 조건
> 패널·수동 매매 표시 등이 이후 추가됐습니다.

- Freqtrade 내장 webhook은 `.format()` 문자열 템플릿만 지원(조건문 불가)이라,
  자체 Flask `/webhook` 릴레이 서버를 만들어 완전한 한글 커스텀 메시지로
  가공한 뒤 Telegram Bot API로 전송하는 구조로 우회 구현
- 실시간 웹 대시보드(Flask + Chart.js, 자체 디자인)
  - 봇별 잔고/손익/승률/MDD, 누적 손익 추이 차트(호버 시 수익률+수익금 동시 표시)
  - 실시간 시세, 포지션/청산 이력 테이블, 최근 알림 모달
  - HTTP Basic Auth로 대시보드 자체 접근 제어
  - 신규 진입/청산 발생 시 Web Audio API로 합성한 알림음 재생 (외부 음원 파일 없음)
  - 멀티 봇이 계좌를 공유할 때 발생하는 잔고 이중계산(다른 봇의 포지션/타 자산 dust
    혼입) 문제를 `is_bot_managed` 필터링으로 해결

### Phase 5 — AWS 배포 (24/7 무중단)
- PC를 꺼도 봇과 대시보드가 계속 동작하도록 AWS EC2(t3.micro, 서울 리전)에 배포
- cloud-init user-data 스크립트로 스왑 메모리 생성 + Docker 자동 설치
- systemd 서비스로 대시보드 자동 재시작, 보안 그룹으로 SSH는 특정 IP만 허용
- DuckDNS 무료 동적 DNS로 고정 도메인 연결

### Phase 6 — 실전 전환 (소액 실계좌)
> ⤷ **Phase 8에서 봇이 교체됨** — 전환 절차(드라이런 검증 → 실자금, API 키 권한
> 제한, DB 분리)는 지금도 그대로 쓰고 있지만, 실전에 올라가 있는 전략은
> 여기 적힌 두 개가 아니라 `BoxBreakoutV2Strategy` 하나입니다.

- 드라이런 충분히 검증 후 소액 실자금으로 전환 (`dry_run: false`)
- 바이낸스 API 키는 출금 권한 비활성화 + IP 화이트리스트 적용 후 발급
- 봇 전환 시점에 드라이런 기록을 별도 DB로 분리해 실계좌 수익률이 드라이런
  데이터와 섞이지 않도록 구성

### Phase 7 — 4번째 종목(XRP) 추가 & 전략 구조 개선
> ⤷ **Phase 8에서 폐기됨** — 이 Phase의 작업(페어별 파라미터 분기, EMA100 추세
> 필터, 5.8년 검증)은 전부 지금은 중단된 두 전략을 대상으로 한 것입니다.
> **검증 방법론과 트러블슈팅은 그대로 유효**하며, 오히려 Phase 8에서 이 방법론을
> 더 밀어붙인 결과로 두 전략을 기각하게 됐습니다.

- **페어 확장 실험**: XRP를 페어에 추가했더니 BTC/ETH/SOL 위주로 튜닝된 공유
  파라미터로는 XRP가 거의/전혀 거래되지 않는 걸 발견 (2년 백테스트 XRP 거래 0건)
- **페어별 파라미터 분기**: 별도 봇 인스턴스를 늘리는 대신(잔고 공유가 안 됨),
  전략 클래스 안에서 `metadata["pair"]`를 보고 XRP일 때만 별도 하이퍼옵트
  파라미터 세트를 쓰도록 분기 처리 — 한 프로세스, 한 잔고 풀을 유지하면서
  종목별로 다른 파라미터를 쓸 수 있게 함
- **구조적 취약점 발견 및 개선**: 실전 배포 직후 백테스트로 재확인하는 과정에서
  평균회귀 전략이 진짜 하락추세에서도 "횡보장"으로 오판해 눌림목을 계속 매수하다
  손절을 반복하는 문제를 발견 (8개월 구간 백테스트 -47.71%, 손절 23건이 -984 USDT로
  나머지 이익을 전부 상쇄). 장기 EMA(100) 방향 필터를 추가해 대세와 반대 방향
  진입을 차단하는 방식으로 개선 (평균회귀는 1% 여유폭 추가)
- **5.8년 워크포워드 + 완전 홀드아웃 검증**: 2020.10~2026.8 전체를 30일 단위로
  재최적화 없이 고정 파라미터로 슬라이딩 검증 + 파라미터 탐색에 전혀 안 쓰인
  2020.8~2021.8 구간을 별도 홀드아웃으로 검증해 과최적화 여부 교차 확인
  (두 전략 모두 70개 구간 중 마이너스 구간 0개, 총 519건 실거래 기준)
- **멀티 봇 계좌 공유의 또 다른 함정 발견**: 두 전략 봇이 같은 종목을 반대
  방향으로 동시에 진입하면, 바이낸스 원웨이 포지션 모드에서 주문이 서로
  넷팅되면서 각 봇의 로컬 거래 기록이 실제 계좌 상태와 어긋나는 현상을 발견
  (`/trades/{id}/reload` API로 재동기화, 안 되면 `DELETE /trades/{id}`로 정리)
- **하이퍼옵트 자체 평가와 실제 백테스트 결과가 크게 어긋나는 현상 확인** —
  하이퍼옵트가 자체 보고한 수익률(예: +16.78%, +4.43%)이 동일 파라미터로 다시
  돌린 독립 백테스트에서는 완전히 다르게(-6.73%, -30.28%) 나오는 경우가 반복
  확인됨 → 이후로는 하이퍼옵트 결과를 그대로 믿지 않고 반드시 별도
  backtesting으로 재검증하는 절차를 필수화

### Phase 8 — 손절 버그 수정, 엣지 검증, 전략 전면 교체
> ⤷ **현재 운용 기준** — 아래 내용이 지금 돌고 있는 봇의 근거입니다.

Phase 7까지의 검증을 통과했다고 생각했던 두 전략을, 진입 신호 자체가 돈을
벌어다 주는지의 관점에서 다시 검증했고 **둘 다 기각**했습니다.

**손절 메커니즘 버그 4건** — 라이브 손절이 의도한 대로 동작한 적이 없었습니다.
- `use_custom_stoploss`가 켜져 있지 않아 `custom_stoploss()`가 아예 호출되지 않음
- `adjust_stop_loss()`의 기준가는 진입가가 아니라 **현재가**. 그래서 `custom_stoploss()`가
  상수를 반환하면 고정 손절이 아니라 **조용히 트레일링 스탑**이 됨
- 반환값이 내부에서 레버리지로 나뉨 → 가격 기준이 아니라 "레버리지 적용 후 계좌 손실률" 기준
- 파라미터 JSON이 클래스 속성을 덮어써서, 코드에 보이는 -0.10 / -0.15 대신
  실제 라이브 손절은 **-0.316 / -0.228** 이었음 (평균 손절 청산이 -32.07%인 것과 정확히 일치)

`stoploss_from_absolute(stop_price, current_rate, is_short, leverage)`로 두 변환을
한 번에 처리하도록 고쳤습니다. `trailing_stop_positive`도 같은 단위 문제를 갖고 있어
(5배에서 0.02 = 가격 0.4%) 껐더니 5.8년 성과가 **-35.54% → -11.77%** 로 바뀌었습니다.

**엣지 검증 (부정적 결과)** — 손절을 고친 뒤에도 두 전략은 수익이 나지 않았고,
원인은 손절이 아니라 진입 신호였습니다. 승률 50%, MFE ≈ MAE, 손절/익절 조합을
격자로 훑어도 **모든 칸이 마이너스**. 같은 종목·같은 기간의 **무작위 진입 대조군을
이기지 못했습니다.**

**검증했다가 기각한 것들**
- **프랙탈 / RSI 다이버전스 / 추세선(빗각)** — 겉보기 성과가 좋았지만 전부 lookahead였습니다.
  스윙 고·저점은 확정에 미래 봉이 필요한데, 백테스트에서 그 시점을 앞당겨 쓰면
  실전에서 존재하지 않는 정보로 진입하게 됩니다. 확정 시점을 정직하게 맞추자 엣지가 사라졌습니다.
- **유튜브에서 가져온 매매법** — 수식으로 기대값을 전개하고 시뮬레이션으로도 반증했습니다.
- **96개 조합 격자탐색** — 학습구간 순위와 검증구간 순위의 **상관계수가 -0.048**.
  즉 "가장 좋은 조합"을 고르는 행위 자체에 의미가 없었습니다. 구간을 바꿔도 일관되게
  살아남은 건 `box_period=12` 하나뿐이라, 그 외의 파라미터는 격자 1등이 아니라
  구간 간 안정성을 보고 정했습니다.

**BoxBreakoutV2 채택** — 무작위 진입 대조군을 통과한 유일한 신호가 박스권 돌파였습니다.
직전 N봉의 고·저를 `shift(1)`로만 참조하는 구조라 lookahead가 원천적으로 불가능합니다.
- 박스 12봉 / 박스폭 4% 이하 / 익절 35%(레버리지 적용 후) / 48시간 시간청산
- 손절은 고정 %가 아니라 **박스 반대편 경계** (롱이면 박스 하단, 숏이면 상단), 최대 5%
- 레버리지 3배. 10배는 백테스트에서 **PF 0.99 / 최대낙폭 98%** 로 무너져서 올리지 않았습니다.

**남은 한계 (정직하게)** — PF는 1.13에 불과하고, 성과가 2024\~2026 구간에 몰려 있습니다.
2023년은 -21.9%였습니다. 큰 엣지가 아니라 "무작위보다는 낫다"가 현재 근거의 전부입니다.

### Phase 9 — 대시보드 실사용 기능
- **봇 전원 버튼** — 열린 포지션이 있을 때 정지하면 그 포지션의 손절/익절 관리도 함께
  멈춘다는 경고를 같이 띄웁니다.
- **열람/조작 권한 분리** — 조회는 로그인 없이, 봇 제어는 로그인 필수. Basic 인증은
  브라우저가 자격증명을 캐시해 "서버가 잊는" 로그아웃이 없어서, 로그아웃 표시 쿠키를
  두고 인증 검사에서 먼저 확인하는 방식으로 구현했습니다.
- **진입 조건 현황 패널** — "봇이 왜 진입을 안 하는가"를 SSH 없이 화면에서 답합니다.
  페어별 박스 범위·박스폭·돌파선까지 남은 거리를 보여줍니다.
- **포지션 상세** — 손절가·익절가·시간청산까지 남은 시간. 이 전략은 손절선이 박스
  경계라 포지션마다 달라서, 진입가 대비 거리를 함께 표시합니다.
- **수동 매매 표시** — freqtrade는 자기가 낸 주문만 압니다. 앱/웹에서 직접 잡은 포지션과
  걸어둔 미체결 주문을 바이낸스 API로 직접 조회(조회 전용)해서 채웠습니다. 미체결 주문은
  그리드로 수십 건이 깔리는 경우가 있어 종목·방향·주문종류로 묶고 클릭하면 펼칩니다.
  이 엔드포인트만은 조회에도 로그인을 요구합니다 — 아직 체결되지 않은 지정가의 가격과
  수량은 남이 보면 그대로 앞에서 채갈 수 있는 정보라서, 다른 조회 API와 성격이 다릅니다.
- **모바일 대응** — 넓은 표는 페이지가 아니라 표 자체가 가로 스크롤되도록 하고,
  좁은 화면용 하단 네비게이션을 따로 뒀습니다.

## 4. 배운 점 / 트러블슈팅 하이라이트
- freqtrade의 `can_short`는 정적 클래스 속성이 아니라 동적 프로퍼티로 둬야
  spot/futures 설정을 한 코드베이스에서 공유할 수 있음
- 멀티 봇이 하나의 거래소 계좌를 공유할 때는 `balance` API의 `bot_owned` 필드만
  믿으면 안 되고, 포지션 단위로 `is_bot_managed` 필터링이 필요함
- 수수료를 특정 코인(BNB)으로 지불하도록 설정된 상태에서 그 코인 자체를
  거래 페어로 쓰면, 소액 오차로 인해 freqtrade가 포지션 종료 동기화를
  거부하는 알려진 엣지케이스가 있음 → 해당 페어를 화이트리스트에서 제외로 대응
- CSS `[hidden]` 속성은 브라우저 기본 스타일이라 우선순위가 낮음 — 직접
  정의한 `.class { display: flex }` 같은 규칙에 쉽게 덮어씌워지므로,
  숨김 처리가 확실히 되어야 하는 요소는 `.class[hidden] { display: none }`
  형태로 명시적 우선순위를 줘야 함
- Windows + Git Bash에서 `docker run -v host:container` 처럼 콜론으로 host/container
  경로를 같이 넘기면, MSYS 경로 자동변환이 컨테이너 쪽 경로까지 Windows 경로로
  잘못 바꿔버려서 볼륨 마운트가 조용히 실패할 수 있음 (`MSYS_NO_PATHCONV=1`로 방지,
  또는 `subprocess.run(["docker", ...])`처럼 셸을 거치지 않고 직접 실행하면 회피됨)
- freqtrade 워크포워드처럼 반복 실행되는 스크립트에서 실패 로그를 그대로
  `print()`하면, Windows 콘솔 인코딩(cp949)이 못 다루는 문자에서 스크립트 전체가
  죽어 나머지 구간이 통째로 스킵됨 — 에러 로그 출력은 항상
  `errors="replace"`로 감싸야 특정 구간 하나의 실패가 전체 실행을 막지 않음
- 하이퍼옵트가 자체적으로 보고하는 "Best result"의 수익률은 실제로 그 파라미터를
  독립 backtesting에 넣었을 때와 다르게 나올 수 있음 — 배포 전 반드시 별도
  backtesting 명령으로 재검증할 것
- freqtrade의 `custom_stoploss()` 반환값은 **현재가 기준**이고 **레버리지로 나뉜다**.
  상수를 반환하면 고정 손절이 아니라 트레일링 스탑이 되어 버리므로, 특정 가격에
  손절을 걸고 싶으면 반드시 `stoploss_from_absolute()`를 쓸 것
- `minimal_roi`와 `trailing_stop_positive`는 가격 변동률이 아니라 **레버리지 적용 후
  계좌 수익률** 단위 (5배에서 `0.20` = 가격 4%)
- 정적 `stoploss`는 안전망일 뿐이고 `custom_stoploss()`는 그보다 **조이는 방향으로만**
  움직일 수 있음 — 정적 값을 커스텀 값보다 느슨하게 잡아둬야 커스텀 손절이 실제로 걸림
- `use_exit_signal = False`면 `custom_exit()`이 아예 호출되지 않아 시간청산이 통째로
  죽음 (레버리지를 올렸는데 성과가 단조롭게 반응하지 않는 것으로 발견)
- `VolumePairList`는 백테스트에서 동작하지 않음 — 백테스트용 설정은 `StaticPairList`로
  바꿔야 함
- 하이퍼옵트의 `--min-trades` 기본값은 1이라, Calmar 같은 지표에서 **"이긴 거래 1건,
  낙폭 0"** 같은 퇴화해가 1등으로 뽑힘 → 목적함수와 무관하게 최소 거래수를 반드시 지정할 것
- 스윙 고·저점을 쓰는 지표(프랙탈, 다이버전스, 추세선)는 확정에 미래 봉이 필요함.
  백테스트에서 확정 시점을 앞당기면 lookahead가 되어 없는 엣지가 보임
- Docker에서 **파일 하나를 bind mount** 하면 컨테이너가 그 파일의 inode를 붙잡음.
  `sed -i`는 파일을 새로 만들어 갈아끼우므로 호스트만 바뀌고 컨테이너는 계속 옛 내용을
  읽음 → 설정 변경 후에는 컨테이너를 recreate 할 것
- `reload_config`는 설정을 다시 읽으면서 `initial_state`도 다시 적용함.
  `initial_state: "stopped"`면 리로드만 해도 봇이 멈추므로, 열린 포지션이 있다면
  리로드 직후 반드시 다시 시작시켜야 함
